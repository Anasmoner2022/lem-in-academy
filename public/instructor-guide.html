Instructor readiness and review

This curriculum is complete as an instructional artifact, with unfinished student implementations. No learner is assessed or marked complete by the hub. Instructors must pilot the work and review solutions before using the track as formal assessment.

Instructor prerequisite gate

  1. Build and test a small Go CLI and explain Reader/Writer ownership, error wrapping and slice aliasing.
  2. Trace BFS, residual cancellation and a minimum-cut witness without relying on a library solver.
  3. Explain both directions of the time-expanded reduction, including room splitting, shared undirected edge gadgets and same-side waiting normalization.
  4. Explain [d,d+n-1], monotone deadline search, integral extraction and why a budget refusal is not infeasibility.
  5. Run the independent occupancy-state oracle and understand its tiny scope and exponential growth.

Before the cohort

Review the source adaptation notes and agree the academy grammar/turn/error policies with local auditors. Check supported Go installation, 64-bit targets, ZIP extraction and all local reading links. Run the publication build and scaffold checks. Pilot the first three projects with a beginner and the exact-planning block with a second reviewer; estimates are planning allowances, not measured cohort medians.

Project review procedure

  1. Ask the learner to show the artifact and one concrete user-facing behavior before discussing implementation.
  2. Walk every component's self-check and verification exit gate. Ask for expected versus actual bytes on a failure case.
  3. Inspect tests with all relevant acceptance skips removed. A green starter compile is insufficient.
  4. Introduce one targeted mutation, such as missing reverse capacity or duplicated tunnel use, and require an existing test to detect it.
  5. Discuss at least two engineering prompts and one practical task. Record feedback in the institution's chosen process; this hub stores no progress.

Core assignment readiness

  • Grammar matrix: counts, terminals, names, integers, unknown commands, link ambiguity and duplicates.
  • Legal movement: identities, adjacency, once-per-ant, shared tunnel use, batch occupancy, completion and end absorption.
  • Exactness: greedy trap, full reduction proof, minimum-deadline proof and independent tiny-state evidence. Do not accept a route-count or shortest-path argument as a substitute.
  • Operational contract: deterministic bytes, stream/exit mapping, no premature echo, checked limits and no false optimum on refusal.
  • Compatibility: official valid/invalid examples, recorded timing cases and a source-revision note.
  • Code review: standard library, clear packages, deliberate errors, gofmt and meaningful tests/fuzzing. No core TODO stub remains.

Planning and support

Core base estimate is 182 hours; with 25–50% review allowance, 228–273. Optional continuation adds 42 base hours. Reserve review sessions after P03, P06, P10, P12 and L01. The optimization block needs explicit hand traces and proof discussion, especially for learners who have never seen flow. Pairing can support reasoning, but each learner should explain the invariants and repair a failed test.

What this delivery verifies

See the validation record for publication links, starter compilation, curriculum structure, algorithm-model evidence and browser review. These are checks of the delivered learning material. They do not certify a completed student solver, cohort outcomes, external audit acceptance or deployment.
